## C01 / P1：新增集成测试遗漏直接依赖，阻断构建

- 位置：[monitorDelivery.integration.test.ts:6](../../packages/scrape/src/integration/monitorDelivery.integration.test.ts#L6)、[scrape/package.json](../../packages/scrape/package.json)。
- 测试显式导入 `drizzle-orm/node-postgres/migrator`，用于 PostgreSQL 测试库迁移。
- `scrape` 的 dependencies、devDependencies 及 workspace 根 package.json 均未声明 `drizzle-orm`；只有 `@anycrawl/db` 声明了 `^0.43.1`。依赖另一个 workspace 包不能代替当前包自己的直接依赖声明。
- Docker 安装步骤已成功，失败发生在 [Dockerfile:57](../../Dockerfile#L57) 的 TypeScript 编译。数据库、AI、libs、template-client 等前置任务已完成，日志显示 4 successful / 5 total。
- 后续 ELIFECYCLE、Turbo failed、exit code 2、buildx failed 是此编译错误逐层向上传递，并非多个独立故障。

最小修复：在 `scrape` 的 devDependencies 声明与 DB 包一致的 `drizzle-orm`，同步 `pnpm-lock.yaml`，并验证冻结锁文件的干净安装及测试模块解析。该导入仅用于测试，不需要为了编译而加入生产运行依赖。

## C02 / P2：生产编译和测试文件的边界未落实

- [scrape/tsconfig.json](../../packages/scrape/tsconfig.json) include 整个 `src`，exclude 只有 node_modules、dist。实际 TypeScript 配置解析确认此 integration test 在编译输入中。
- [.dockerignore:18](../../.dockerignore#L18) 的 `__tests__`、`*.test.*`、`*.spec.*` 未使用递归匹配，未过滤 monorepo 深层测试文件。真实 Docker 日志直接证明该文件进入了 build context 和 tsc。
- Docker 的 `**` 才能匹配任意层目录；可使用 `**/__tests__`、`**/*.test.*`、`**/*.spec.*` 表达递归排除。参见 [Docker 官方匹配规则](https://docs.docker.com/build/concepts/context/#matching)。
- 仅修正 Docker 排除规则会隐藏 Docker 的这一个触发点，但 Vercel 不使用 Docker context，且集成测试仍缺直接依赖，因此不能作为 C01 的完整修复。

建议：生产编译使用明确的 build tsconfig；单独保留覆盖测试文件的类型检查和 Jest 集成测试。Docker 文件过滤作为补充。验收应检查生产 dist 不含测试输出，并确认新增测试仍被测试命令发现、执行。

将同一解析器的文件可见范围限制在仓库后，结果变为未解析。此操作没有移动或删除用户目录依赖；它是依赖解析核查，不是完整 Docker 构建复现。

本地构建成功依赖了仓库之外、版本还不同的包，因此不能证明干净环境可构建。此前完成的真实 API/DB/Redis/SMTP/HTTP E2E 结果仍成立；缺失的是对干净安装、声明完整性和最终 Docker 镜像的验收。此前验收文档中的“构建通过”应限定为当时本地环境，不能推导为远端 CI 或 Docker 已通过。

1. 补齐测试直接依赖并同步 lockfile，保留 PostgreSQL/SQLite 真实迁移测试。
2. 明确生产 build 与测试类型检查的边界；修正 Docker 的递归过滤。不能通过跳过集成测试宣称修复完成。
3. 在没有用户目录 node_modules、旧 dist 或 Turbo 构建缓存的环境，使用仓库固定的 pnpm 10.12.4 冻结安装，然后运行与 Docker 一致的构建命令。
4. 分别复验 amd64、arm64 镜像和 Vercel docs 的完整 Turbo 依赖构建；前置 tsc 通过不等于整个镜像已通过，后续尚有原生依赖、浏览器安装和运行阶段。
5. 重新执行受影响的双数据库通知集成测试，并确认测试依赖来自声明中的版本。随后再更新 PR 验收状态。
